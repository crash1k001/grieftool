# GriefTool: спецификация магазина

## Цель и согласованные решения
Публичный русскоязычный магазин Minecraft-сервера mc.GriefTool.fun и защищённая админка. Пользователь выбрал JavaScript, тёмное оформление по предоставленным примерам и оранжевые акценты вместо голубых. Развёртывание одним приложением на VPS через Docker с постоянным хранилищем. Обычный хостинг только для статических файлов не подходит.

## Стек и устройство
Next.js на JavaScript и Node.js LTS, SQLite для одного экземпляра приложения. Серверные обработчики работают с базой; браузер не получает секреты. Отдельные модули отвечают за каталог, расчёт цены, заказы, авторизацию и настройки. CSS использует общие токены цветов, размеров и состояний. Зависимости фиксируются lockfile.

## Публичный интерфейс
Адаптивная шапка с логотипом GT, навигацией и копированием IP. Большой слайдер с оригинальными игровыми иллюстрациями, оранжевым градиентом и инструкцией подключения. Ниже — баннер сервера, категории, карточки товаров, выбор количества игровой валюты, подтверждённые последние покупки, FAQ и подвал. На мобильном категории доступны без горизонтального переполнения. Клавиатурная навигация, заметный фокус, подписи полей, достаточный контраст и reduced-motion обязательны.

Кнопка покупки открывает форму с товаром, сроком или количеством, ником и промокодом. Сервер проверяет ник, доступность товара и применимость скидки, сам рассчитывает сумму в целых копейках. Клиентская цена не является доверенной. Ошибки показываются рядом с полями; повторная отправка блокируется на время запроса. Реальные последние покупки появляются только после подтверждённой оплаты; при отсутствии покупок отображается честное пустое состояние. Онлайн не выдумывается: при отсутствии интеграции показывается «Статус не подключён».

## Админка
Вход по паролю без публичной регистрации. Начальные учётные данные задаются переменными окружения, пароль хранится как стойкий хеш. HttpOnly-сессии с ограниченным временем действия; Secure в production, SameSite, проверка Origin для изменяющих запросов, ограничение попыток входа. Каждый административный endpoint проверяет сессию на сервере.

Разделы: обзор заказов и подтверждённых продаж; CRUD категорий и товаров (название, описание, цена, старая цена, срок, тип, доступность, иллюстрация из встроенного набора); скидки и промокоды (процент, даты, минимальная сумма, лимит использования); просмотр и фильтрация заказов; настройки названия, IP, баннеров, FAQ, правил и контактных ссылок; журнал административных изменений. Произвольный HTML из админки не исполняется. Недействительные ссылки скрываются.

## Заказы, платежи и выдача
Заказ содержит снимок товара, ник, итоговую сумму, промокод, дату и независимые статусы оплаты и выдачи. Переход к оплате отключён с понятным сообщением, пока провайдер не настроен. Секреты не запрашиваются в чате и не записываются в Git. В первоначальный этап входят каталог, расчёт и создание ожидающего заказа; реальный приём платежей и выдача не симулируются.

Подключение конкретного провайдера и серверного плагина — следующий этап после выбора пользователем этих сервисов. Он потребует проверки подписей webhook, суммы и валюты, уникального идентификатора события, идемпотентной обработки и очереди выдачи с повторами. До реализации этих проверок автоматическая оплата и выдача остаются недоступными. Управление игровым сервером через консоль, банами и файлами не входит в админку магазина.

## Данные и эксплуатация
SQLite содержит категории, товары, промокоды, заказы, сессии, настройки и журнал действий. Миграции повторяемы; демонстрационные товары отмечены как примеры и не создаются повторно. Заказы и настройки сохраняются при перезапуске. База и резервные копии находятся в постоянном Docker volume, секреты — в окружении. Публичный health endpoint проверяет доступность приложения и базы, не раскрывая внутренние данные.

README описывает локальный запуск, переменные окружения без секретных значений, сборку, Docker Compose, домен и HTTPS через обратный прокси, первичный вход, резервное копирование согласованным SQLite backup API и восстановление при остановленном приложении. Публикация на реальный хостинг требует доступа к выбранному хостингу и не считается выполненной локальной сборкой.

## Проверки и критерии приёмки
Production-сборка проходит. Автотесты проверяют серверный расчёт скидок и сроки промокодов, валидацию ника, защиту административных endpoints, вход/выход, CRUD товара, создание заказа и сохранение после перезапуска. Браузерная проверка покрывает каталог, фильтры, форму покупки, честное отключение оплаты, редактирование товара в админке, мобильный экран и отсутствие ошибок консоли. Неавторизованный пользователь не может изменять данные. Ни онлайн, ни продажи, ни успешная оплата не изображаются как реальные без источника подтверждения.

## Порядок работ
Сначала реализуется единое приложение магазина и админки по этой спецификации, затем выполняются сборка и проверки и готовятся инструкции развёртывания. Интеграция платежей и выдачи выполняется отдельным этапом с выбранными сервисами. Проект использует существующий checkout /workspace/grieftool; отдельный worktree не требуется.
